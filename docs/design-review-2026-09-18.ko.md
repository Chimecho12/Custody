# 데스크톱 콘솔 디자인 검토

검토일: 2026-09-18. **이 문서는 제안이며, 아래 디자인 변경은 적용하지 않았습니다.**

## 대상과 확인 범위

화면 검토 대상은 `design/workbench-console`의 `6239fde` ([PR #9](https://github.com/Chimecho12/Custody/pull/9))입니다.
구조 리팩토링은 `develop`의 `0a50015`에서 시작했습니다. 따라서 이 문서의 워크벤치 화면·CSS 지적은
리팩토링 브랜치의 화면과 일부 다릅니다. 아래 소스 링크는 검토한 커밋으로 고정했습니다.

빌드한 브라우저 미리보기에서 9개 화면을 1320px·900px 너비로 확인하고, 요청·기록 검색·사건 조사·배포 단계 이동을 실행했습니다.
추가로 요청·사건 기록·연결·배포 설정·감사 자료를 1320px·900px·760px에서 확인하고,
정책 선택의 키보드 조작과 패널 안내문의 잘림을 측정했습니다. 지도 행동 메뉴와 다크 테마도 확인했습니다.
추가 확인 시 모션 감소 설정과 화면 전환 후 대기를 적용해 전환 중의 흐린 화면을 가독성 결함으로 판단하지 않았습니다.

확인한 너비에서는 문서 전체의 가로 넘침과 브라우저 실행 오류가 없었습니다. 다만 이는
패널 안의 모든 글자가 보이거나 모든 키보드 조작이 가능한지를 보장하지 않습니다.
네이티브 앱의 IPC·파일 선택기, 실제 여러 컴퓨터 배포, 외부 클라우드 LLM 호출은 이 화면 검토의 범위 밖입니다.
명도 대비의 수치 측정, 스크린리더 실기 검증, 비전공자 사용성 실험도 수행하지 않았습니다.

아래에서 **확인**은 코드 또는 실행 화면에서 관찰한 사실이고, **영향**은 그 사실에서 예상되는 사용성 문제입니다.
기존 화면의 개선 제안이므로 모두 이번 구조 리팩토링에는 `[선택 개선]`입니다. 우선순위는 후속 디자인 작업의 순서이며
리팩토링 PR에 별도 화면 변경을 요구하는 병합 조건이 아닙니다.

## D01. 근거 부족을 실패와 같은 색으로 표시합니다

- **확인:** 요청 결과의 T 판정 배지와 사건 기록의 T 열은 `passed`만 녹색이고 나머지 값은 빨간색입니다.
  영수증 결손 표본의 `insufficient_evidence`도 빨간색으로 표시됩니다. 다른 상세 화면에는 근거 부족을 별도로 구분하는 코드가 있습니다.
- **발생 조건·영향:** 증거가 부족해 판단하지 못한 사건을 조회하면 검증 실패가 확정된 사건과 같은 신호를 받습니다.
  비전공자는 이를 변조 확정으로 읽을 수 있습니다. 로컬 검증 결과와 T의 근거 부족도 구분해야 합니다.
- **제안:** `통과 / 실패 / 근거 부족 / 판정 대기`를 일관된 한국어·기호·색 조합으로 표현해 주시면 좋겠습니다.
  근거 부족은 위반 확정이 아니라는 짧은 설명을 함께 제공하고 원래 상태 코드는 상세에서 유지합니다.
- **확인 기준:** 같은 네 상태를 요청 요약·사건 목록·사건 상세에서 비교했을 때 뜻이 일치하고,
  색을 구분하지 못해도 텍스트만으로 상태를 식별할 수 있어야 합니다.
- **근거:** [요청 결과](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/src/features/request/view.ts#L225),
  [사건 목록](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/src/features/history/controller.ts#L50).

## D02. 라디오 그룹의 키보드 선택 방식이 불완전합니다

- **확인:** 정책 버튼은 `radiogroup` 안의 `role="radio"`이고 모두 `tabIndex=0`입니다.
  첫 정책에 초점을 둔 뒤 `ArrowRight`를 눌러도 초점과 선택은 첫 항목에 남았습니다.
  정책·실험 조건의 핸들러는 클릭 중심이며, 지도 행동 메뉴의 라디오 버튼에도 방향키 선택 처리가 없습니다.
  지도 노드의 Enter·Space 열기와 Escape 닫기는 이미 구현되어 있습니다.
- **발생 조건·영향:** 키보드로 정책이나 지도 실험 조건을 바꾸는 사용자는 라디오 그룹에서 예상한 조작을 할 수 없습니다.
  탭으로 모든 버튼을 순회해 실행할 수 있으므로 전체 기능이 키보드로 불가능하다는 뜻은 아닙니다.
- **제안:** 네이티브 라디오 입력을 쓰거나 선택 항목만 탭 진입점으로 두고 방향키로 이동·선택해 주시면 좋겠습니다.
  라디오에 중복된 `aria-pressed` 대신 선택 의미를 일관되게 표현합니다.
- **확인 기준:** 마우스 없이 정책·실험 조건을 선택하고 요청을 실행할 수 있어야 합니다.
  지도에서 고른 값, 상단 폼의 값, 접근성 속성의 선택 상태가 같아야 합니다.
- **근거:** [정책·시나리오 렌더링](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/src/features/request/controller.ts#L69),
  [지도 메뉴와 키보드 처리](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/src/shared/flow.ts#L394).

## D03. 공유·보관에 필요한 안내가 제목 옆에서 잘립니다

- **확인:** `.itx-panel-meta`는 한 줄·말줄임으로 제한됩니다. 1320px 너비에서도 배포 신원 생성의
  `공유할 파일은 operator.json · 개인키와 운영자 폴더는 이 PC 에 보관`이 잘렸습니다.
  감사 자료의 공개 패키지 안내와 W의 본문 미수신 안내도 `scrollWidth > clientWidth`였습니다.
- **발생 조건·영향:** 넓은 창의 2열 패널에서 파일을 공유하는 사용자가 중요한 보관·공유 범위를 끝까지 읽지 못할 수 있습니다.
  좁은 창에서는 1열로 바뀌어 해당 문구가 오히려 더 잘 보였습니다.
- **제안:** 실행 판단에 필요한 안내를 패널 본문 또는 실행 버튼 근처의 줄바꿈 가능한 설명으로 옮겨 주시면 좋겠습니다.
  제목 옆에는 짧은 상태만 두고, 긴 설명을 툴팁으로만 제공하지 않습니다.
- **확인 기준:** 1320px·900px·760px와 글자 확대 상태에서 공유할 파일과 보관할 파일의 안내를 모두 읽을 수 있어야 합니다.
- **근거:** [패널 메타 CSS](https://github.com/Chimecho12/Custody/blob/6239fde/itx/ui/workbench.css#L46),
  [배포 안내](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/index.html#L235).

## D04. 다음 행동의 표현을 실제 요청 동작과 맞출 필요가 있습니다

- **확인:** 격리·취소·오류 후 안내에 `같은 계약으로` 재요청한다는 표현이 있습니다.
  실제 `Agent.request`는 요청마다 새로운 시도·salt·nonce와 서명된 계약을 만듭니다.
  T 시간 초과 시에는 `기본 보호로 낮춥니다`라는 안내가 있지만 그 문장 자체에는 제3자 확인을 기다리지 않게 된다는 설명이 없습니다.
- **발생 조건·영향:** 문제 발생 후 안내를 따르는 사용자가 동일 계약의 재전송과 새 요청을 혼동하거나,
  요청을 빨리 완료하려고 정책을 바꾸면서 달라지는 확인 범위를 놓칠 수 있습니다.
- **제안:** `같은 입력으로 새 요청을 시작`처럼 실제 동작을 설명해 주시면 좋겠습니다.
  정책 변경 안내에는 `다음 요청부터 적용` 및 제3자 판정을 기다리는지 여부를 함께 표시합니다.
  기존 사건의 계약·판정이 바뀌는 것처럼 표현하지 않습니다.
- **확인 기준:** 재요청 전후 식별자가 다르다는 사실과 화면 문구가 일치하고, 정책 변경 후 과거 사건의 결과는 그대로 남아야 합니다.
- **근거:** [다음 행동 문구](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/src/features/request/view.ts#L191),
  [새 계약 생성](https://github.com/Chimecho12/Custody/blob/6239fde/itx/runtime/agent.py#L220).

## D05. 연결 흐름이 파일·역할 지식을 먼저 요구합니다

- **확인:** 연결 화면은 `U의 config.json 절대 경로`를 요구하며 환경·운영 주체·역할별 주소·공개키를 보여 줍니다.
  배포 설정에는 5단계 안내가 있지만, 첫 진입 시 `이 PC에서 서비스 준비`와 `다른 PC의 서비스에 연결`이라는 목적별 시작점은 없습니다.
- **발생 조건·영향:** 비전공자는 어느 PC에서 어떤 역할을 준비해야 하는지, 현재 연결된 모델이 모형인지 로컬 추론인지
  외부 서비스인지 파악하기 전에 설정 파일과 U/R/M/T를 이해해야 합니다.
- **제안:** 목적 선택 → 필요한 역할·파일 안내 → 설정 선택 → 연결 요약 확인의 흐름을 검토해 주시면 좋겠습니다.
  파일 선택과 함께 역할·주소·모델 종류를 읽기 쉬운 요약으로 보여 주고 기존 상세 정보를 접어 볼 수 있게 합니다.
  클라우드 연동 항목은 실제 지원되는 어댑터와 검증 범위가 있을 때만 제공해야 합니다.
- **확인 기준:** 사전 설명을 듣지 않은 사용자가 자신의 PC 역할과 연결할 주소를 설명할 수 있어야 합니다.
  `연결됨`을 모델 실행의 진위나 독립 운영이 증명되었다는 뜻으로 읽게 만들지 않아야 합니다.
- **근거:** [연결 입력](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/index.html#L209),
  [연결 요약](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/src/features/connection/controller.ts#L26).

## D06. 지도 제어의 진입점과 확대 상태를 개선할 여지가 있습니다

- **확인:** 최초 요청 화면에서는 경로 상세가 접혀 있고 `그림에서 고르기`로 행동 메뉴에 진입합니다.
  메뉴에는 이미 `다음 요청에서`라는 설명이 있습니다. 1320px의 2열 화면에서 지도 메뉴를 열면
  확인한 표본은 45% 배율로 전체 노드를 맞추며 노드 안의 글자가 작아지고 메뉴가 일부 노드 위에 놓입니다.
  캔버스 위의 모든 휠 이벤트는 기본 스크롤을 막고 확대·축소합니다.
- **발생 조건·영향:** 지도를 제어 도구로 쓰려는 사용자가 조작 가능한 위치를 찾기 어렵거나,
  아래 내용을 읽으려고 스크롤하다 지도를 확대할 수 있습니다. 과거 사건 검사와 다음 요청 설정도 혼동할 여지가 있습니다.
- **제안:** `다음 요청 조건을 지도에서 설정` 같은 진입점과 선택 결과 요약을 제공해 주시면 좋겠습니다.
  상세 검사를 위한 넓은 지도 보기, 읽을 수 있는 기본 배율, 일반 페이지 스크롤과 구분되는 확대 조작을 검토합니다.
  레이아웃 알고리즘 이름은 고급 설정으로 옮길 수 있습니다.
- **확인 기준:** 지도에서 R의 조건을 고르면 상단 폼과 다음 요청에 같은 값이 반영되어야 합니다.
  과거 사건을 보는 동안 선택한 조건이 그 사건의 증거를 바꾸는 것처럼 보이지 않아야 합니다.
- **근거:** [지도 도구 모음](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/src/shared/flow.ts#L166),
  [휠 처리](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/src/shared/flow.ts#L457).

## D07. 좁은 화면에서 입력이 결과와 지도를 밀어냅니다

- **확인:** 1100px 이하에서는 워크벤치가 1열이 됩니다. 900×920 화면의 초기 상태에서는 요청 입력이
  대부분의 첫 화면을 차지하고 결과 요약은 아래쪽에서 시작합니다. 지도는 그보다 아래에 있습니다.
  같은 너비에서 사이드바의 환경 식별자도 끝까지 표시되지 않았습니다.
- **발생 조건·영향:** 노트북 크기의 창에서 요청을 실행하고 결과를 읽은 뒤 조건을 바꿔 재실행하는 작업에
  반복적인 스크롤이 필요할 수 있습니다. 가로 넘침이 없다는 사실만으로 이 흐름이 편하다고 할 수는 없습니다.
- **제안:** 실행 후 결과로 이동하는 명확한 동작, 접을 수 있는 입력 요약, 결과에서 조건 편집으로 돌아가는 링크를 검토해 주시면 좋겠습니다.
  환경 식별자는 줄바꿈 또는 확장 가능한 상세로 전체 값을 확인할 수 있게 합니다.
- **확인 기준:** 900×920과 760×920에서 실행 → 결과 확인 → 지도 조건 변경 → 재실행을 수행하고,
  현재 요청과 다음 요청 설정을 구분할 수 있는지 확인합니다. 자동 이동을 추가한다면 사용자 초점을 예측 가능하게 유지해야 합니다.
- **근거:** [반응형 전환](https://github.com/Chimecho12/Custody/blob/6239fde/itx/ui/workbench.css#L37),
  [요청 화면 구성](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/index.html#L54).

## D08. 시나리오의 검증 실패와 방어 성공을 함께 읽기 어렵습니다

- **확인:** 참조 시나리오 카드의 큰 상태는 판정에 따라 `통과` 또는 `실패`이고, 게이트 결과는 별도 세부 정보입니다.
  공격이 검출되어 응답이 격리된 표본도 검증 실패를 전면에 표시합니다.
- **발생 조건·영향:** 시연을 처음 보는 사용자는 공격 탐지 후 격리한 정상 방어를 도구 자체의 실패로 해석할 수 있습니다.
- **제안:** 요청 화면에 이미 있는 `검증 결과 / 응답 공개 여부`의 두 축을 시나리오 카드에도 적용해 주시면 좋겠습니다.
  예를 들어 `변조 검출 · 응답 격리`처럼 두 결과를 함께 설명하되 검증 실패를 통과로 바꾸지는 않습니다.
- **확인 기준:** 정상·변조·증거 결손·T 시간 초과 표본을 보고 사용자가 무엇이 확인되었고 응답이 공개되었는지 각각 답할 수 있어야 합니다.
- **근거:** [시나리오 카드](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/src/features/simulation/view.ts#L145).

## D09. 작업 결과가 다음 행동으로 이어지는 요약을 제공하지 않습니다

- **확인:** 공통 작업 바인딩은 결과를 `pretty(result)`로 출력하고 `작업 결과와 저장 경로를 확인하세요`라는 공통 알림을 사용합니다.
  배포·자료 내보내기에서는 결과 JSON에서 필요한 파일과 다음 단계를 찾아야 합니다.
- **발생 조건·영향:** 파일을 만든 사용자가 어떤 파일을 다른 PC에 전달할지, 다음 단계에 무엇을 입력할지 결정하는 데 어려움이 있을 수 있습니다.
  단계 이동과 실제 작업 완료도 별개의 상태이므로 구분을 계속 유지해야 합니다.
- **제안:** 결과 상단에 완료한 작업·생성 파일·저장 경로·다음 행동을 표시하고 원본 JSON은 상세로 제공해 주시면 좋겠습니다.
  공유용 파일과 로컬 보관 파일을 구분하며, 단순 단계 이동을 실제 작업 성공으로 표시하지 않습니다.
- **확인 기준:** 신원 생성·배포 제안·활성화·증거 내보내기 각각에서 원본 JSON을 해석하지 않고도 다음 입력 파일을 찾을 수 있어야 합니다.
- **근거:** [공통 작업 출력](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/src/shared/actions.ts#L15),
  [배포 출력 패널](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/index.html#L295).

## D10. 전문 용어와 작은 메타 정보가 기본 화면에 밀집합니다

- **확인:** 일반 요청·연결 화면에도 U/R/M/T, `network_lab`, `single_operator`, `nonce`, 모델 종류와 해시가 노출됩니다.
  패널 메타 정보에는 작은 글자와 고정폭 서체가 널리 쓰이며, 지도 전체 보기에서는 추가로 축소됩니다.
  환경 안내는 사이드바·상단·미리보기 안내·하단에 나누어 반복됩니다.
- **발생 조건·영향:** 기술 경험이 적은 사용자는 요청의 결과보다 용어 해석에 시간을 쓰거나 작게 표시된 설명을 놓칠 수 있습니다.
  읽기 어려움의 정도는 사용자 실험이 필요하며, 이 검토로 명도 대비 기준 위반을 확정하지는 않습니다.
- **제안:** `R · 중계자`, `T · 제3자 검증자`처럼 평이한 이름을 먼저 제공하고 전문 식별자는 상세에 유지해 주시면 좋겠습니다.
  일반 설명은 본문 크기와 서체로, 해시·주소만 고정폭으로 구분합니다. 환경 요약의 위치를 정리하되 모형·실험 환경 표시는 항상 알아볼 수 있어야 합니다.
- **확인 기준:** 라이트·다크·시스템 테마와 200% 확대에서 핵심 설명을 읽을 수 있는지 확인하고,
  실제 색 조합의 명도 대비를 측정합니다. 비전공자가 역할과 검증 한계를 자신의 말로 설명하는지도 확인합니다.
- **근거:** [연결 정보](https://github.com/Chimecho12/Custody/blob/6239fde/desktop/src/features/connection/controller.ts#L26),
  [워크벤치 스타일](https://github.com/Chimecho12/Custody/blob/6239fde/itx/ui/workbench.css).

## D11. 제목 언어와 테마 조작의 통일은 선택 사항입니다

- **확인:** 한국어 탐색 메뉴 아래에 `Request`, `Response`, `Configuration`, `Output` 같은 영어 패널 제목이 함께 쓰입니다.
  테마는 하나의 버튼을 눌러 시스템·라이트·다크를 순환하는 방식입니다.
- **판단:** 시각적 취향과 제품의 사용자층에 따른 선택입니다. 이것만으로 기능 결함이나 병합 차단 사유가 되지는 않습니다.
- **제안:** 한국어 제목을 기본으로 하고 영어 식별자는 보조로 둘지, 테마를 명시적인 선택 메뉴로 보여 줄지 통일하면 좋겠습니다.
- **확인 기준:** 사용자가 현재 테마와 다음에 적용할 테마를 예측할 수 있고, 같은 개념이 화면마다 다른 이름으로 나오지 않으면 충분합니다.

## 유지하면 좋은 부분과 후속 확인 순서

요청 결과가 검증과 응답 공개 여부를 분리하는 점, 실제 측정과 시간선 추정을 구분하는 설명,
모형·단일 운영자 환경 표기, 모션 감소 설정 지원, 해시 복사, 지도 조건과 폼의 연동은 유지할 가치가 있습니다.
서버 주소에 연결된 사실과 독립된 제3자가 기여한 사실, 서명된 자기보고와 실제 모델 실행 증명도 계속 구분해야 합니다.

후속 디자인 작업은 D01~D04의 의미·조작·안내를 먼저 정리하고 D05~D09의 작업 흐름을 검증한 뒤,
D10~D11의 표현을 조정하는 순서가 적절합니다. 시각적 장식보다 다음 과제를 관찰하는 사용성 검증을 권합니다.

1. 연결된 환경이 모형인지 실제 추론인지, 이 PC와 다른 PC가 맡은 역할이 무엇인지 설명하기
2. 지도에서 다음 요청의 중계 조건을 바꾸고 폼과 같은 값인지 확인하기
3. 변조 검출·근거 부족·T 시간 초과를 구분하고 응답 공개 여부를 읽기
4. 결과 파일 중 공유 가능한 것을 찾아 다른 PC에서 이어갈 단계를 설명하기
5. 키보드만으로 같은 과제를 수행하고 좁은 창·글자 확대에서 상태를 놓치지 않기

이 결과는 화면·표본 데이터에 대한 검토입니다. 실제 클라우드 LLM 내부 동작 검증이나 다중 PC 운영의
무결성·가용성을 입증하는 자료로 사용해서는 안 됩니다.
